# 项目工作方式：一个人 + 多个 Agent

这份文档写给人看，说明这个项目怎么记录、怎么拆任务、怎么让多个 Agent 一起干活而不互相踩脚。Agent 要遵守的规则写在根目录的 [AGENTS.md](../AGENTS.md)。

## 核心原则：仓库就是共享记忆

Agent 不记得上一次对话，换一个会话、换成另一个工具，记忆也都清零。所以**凡是下一个 Agent 需要知道的，都写进仓库里的文件**，不要只留在聊天记录里。

判断标准：如果明天开一个全新会话，它需要先知道这件事才能不犯错，那就必须写下来。

## 记录什么、写在哪（三层）

| 层 | 文件 | 写什么 | 多久变一次 |
| --- | --- | --- | --- |
| **规则层** | `AGENTS.md` | 项目是什么、命令、硬性规则、代码地图、协作流程。保持短，它是地图不是手册 | 很少改 |
| **状态层** | `docs/STATUS.md` | **交接单**：现在到哪了、什么能用、什么坏了、下一步、待你拍板的问题 | 每次会话结束 |
| | `docs/BOARD.md` | **任务板**：每个任务的编号、状态、谁在做、说明书链接 | 任务状态一变就改 |
| | `docs/plan/exec-plan.md` | **执行计划**（多阶段项目才需要）：分工、依赖图、每个阶段走完的标志、待拍板的决定 | 阶段变化时 |
| **知识层**（只增不改） | `docs/specs/T-xxx-*.md` | **任务说明书**：目标、验收标准、能改哪些文件、不做什么 | 开工前写好 |
| | `docs/adr/NNNN-*.md` | **决策记录**：为什么选 A 不选 B | 做重要决定时 |
| | `docs/research/*.md` | **调研笔记**：外部 API、协议、价格、限制，附出处和日期 | 调研完一次写一次 |
| | `docs/experiments/*.md` | **实验记录**：比较几个方案，判定标准在跑之前写好 | 需要用数据做决定时 |
| | `evals/cases/*.md` | **回归用例**：真实使用中出过的错，每个错一条（项目调用模型时才需要） | 每次出错 |
| | git 提交 | 改了什么 | 每完成一步 |

最容易漏的三样：

1. **为什么**：代码只记录「是什么」，选型理由要写进 ADR，否则下次会被另一个 Agent 改回去。
2. **验收证据**：「测试通过」「真机跑通」要写明怎么验的、哪天验的，记在 STATUS 的验收记录里。
3. **外部资料**：查过的厂商文档要写进 research，否则每个 Agent 都会重新查一遍，结论还不一样。

## 三条工程纪律

记录解决的是「不忘」，这三条解决的是「不退步」。

### 1. 出过的错都变成用例

每次真实使用中发现错误，先把它存成一条能重现的用例，再修。修好之后这条用例一直留着，以后每次改动都跑一遍。

- 代码的 bug：写成一个失败的测试，修好后它变绿。
- 模型输出的错误（摘要漏了要点、分类错了、编造了内容）：存进 `evals/cases/`，写明输入、期望和实际输出、怎么判定。改提示词或换模型之前，先跑一遍这些用例。

用例只来自真实出过的错，不凭空编。攒到几十条，它就是这个项目自己的评测集，比任何公开榜单都更能说明「改了之后是变好还是变坏」。

### 2. 每次模型调用都留痕

项目里只要调用模型（或者别的按量付费的服务），每次调用都记一行：用了哪个模型、哪一版提示词、输入输出各多少 token、花了多少钱、花了多久、成功还是失败。

没有这些记录，出了错没法重现，账单涨了也不知道是哪一步涨的。两条配套规则：

- **提示词是代码**：放在文件里、带版本号，改动走评审。
- **花钱先估算**：付费调用第一次真实运行之前，先写出估算（次数 × 单价），得到你的确认。

### 3. 规则靠检查执行，不靠提醒

写在文档里的规则，Agent 会忘，人也会忘。一条规则只要能被机器检查，就写成检查：

| 想守住的事 | 写成什么 |
| --- | --- |
| 模块之间的依赖方向、数据不能越界 | 结构测试、属性测试 |
| 类型、格式、测试都要过 | CI，不过不能合并 |
| 任务板和说明书对得上、文档链接没断、交接单没过期 | `flow check`（体检脚本，也可以放进 CI） |
| 合并前要有验收证据 | PR 模板里的勾选项 |

同一类错误出现第二次，就该问一句：能不能让机器拦住它？能，就加一条检查；AGENTS.md 里对应的规则后面注明「由什么检查」。

## 角色分工

| 角色 | 谁 | 负责 |
| --- | --- | --- |
| **产品负责人** | 你 | 定方向、拍板、验收，提供密钥、账号和硬件 |
| **总控** | 主会话 | 拆任务、写说明书、维护 BOARD / STATUS、合并分支、改共享文件 |
| **执行者** | 任务会话（一个任务一个会话） | 按说明书实现，测试和审查都通过才算完成 |
| **专家** | 子代理（会话内部派出，用完即走） | 审查、安全检查、查资料、写测试 |

模型按活儿选：写说明书、做架构和评审，用最强的模型，因为说明书写错了，后面全错；按说明书实现，用主力编码模型；调研和批量杂活，用便宜的模型。

## 任务生命周期

```text
想法 ──► Inbox ──► 写说明书 ──► Ready ──► 开任务会话 ──► In progress ──► 测试 + 审查 ──► Review ──► 合并 ──► Done
                  (验收标准)              (worktree 分支)                    (PR + CI)                 更新 STATUS
                                                                                                    重要决定写 ADR
```

不做了的任务移到 `Voided` 并写明原因，编号不复用。

## 计划和实验

- **计划也是文件。** 项目分成几个阶段时，把分工、依赖关系、每个阶段「走完的标志」和需要你拍板的决定写进 `docs/plan/exec-plan.md`。计划变了就改文件，旧的决定留在 ADR 里。小项目不需要它，任务板就够了。
- **实验要先写判定标准。** 要在几个方案之间用数据做选择时（哪个模型、哪种切分方式），先在 `docs/experiments/` 里写下比什么、怎么算赢，再跑。跑完再定标准，结论就不可信了。实验不提前做：等到真有决定要做、手里有真实数据时再做。

## 并行规则

1. **一个任务 = 一个会话 = 一个 git worktree 分支。** 互不影响，做砸了直接丢掉分支。
2. **按目录切分，同一时间一个文件只能有一个执行者。** 架构设计时就有意把主线放进不同目录，好让它们能并行。
3. **共享文件由总控改**：入口文件、配置结构、数据库迁移、依赖清单。执行者需要改它们时写进说明书，合并时由总控统一处理。
4. **调研随时可以并行**：它只往 `docs/research/` 写新文件，不碰代码。
5. **同时最多 2～3 个执行者。** 瓶颈是你审查的速度，不是 Agent 的数量。

## 用 GitHub 时

- `main` 分支受保护：不直接推送，只通过 PR 合并。
- 一个任务一个分支 `task/T-xxx-简短名`，一个 PR。PR 模板要求写清楚任务编号、验收证据和安全自查。
- CI 跑「完成的定义」里的检查和体检脚本，不通过不能合并。
- 合并用 squash，提交信息写 `<类型>: T-xxx 简述`。
- 推送和开 PR 是往外发的动作，要你开口才做。

## 一次典型的开发日

1. 打开主会话（会自动读 STATUS 和 BOARD，并做一次体检），问「下一步做什么」。
2. 总控从 BOARD 里挑出 Ready 的任务；彼此独立的任务各开一个任务会话。
3. 你去忙别的。任务会话做完会报告，总控核对结果并合并。
4. 用的时候发现哪里错了，说一句「记一条用例」，它就不会再悄悄错第二次。
5. 结束前做一次交接，把 STATUS 更新好。下次谁接手都能续上。

## 和别人协作

`AGENTS.md` 是通用格式，Codex、Cursor 等工具都会读；`CLAUDE.md` 只是引用它。不同人用不同工具，也遵守同一套规则、读同一份 STATUS 和 BOARD。BOARD 上的「谁在做」写人名或会话名，避免两个人同时动同一个任务。
