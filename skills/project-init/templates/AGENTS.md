## 硬性规则

- **不提交密钥**：密钥只放 `.env` 或系统凭据库，并确保它们已被 git 忽略。新增配置项时同步更新示例配置文件。
- **测试先行**：新功能、修 bug 先写失败的测试。外部服务用假实现或录制的响应；真实调用（要花钱、会往外发消息的）放在单独的脚本里，不放进常规测试。
- **只改说明书允许的文件**：需要改范围外的文件时，先更新说明书。
- **出错先留用例**：真实使用中发现的错误，先存成一条能重现它的回归用例，再修。代码的 bug 写成失败的测试；模型输出的错误存进 `evals/cases/`。
- **规则靠检查执行**：一条规则只要能写成测试、CI 检查或 hook，就写成检查，并在规则后面注明由什么检查。只写在文档里的规则迟早被忘掉。

## 协作流程

1. **领任务**：在 `docs/BOARD.md` 把任务改成 `In progress`，填上「谁在做」。一个任务一个分支：`task/T-xxx-简短名`。
2. **只改说明书允许的文件**。发现需要改别的地方，先停下来更新说明书，或在 STATUS 里记一个问题。
3. **做完**：自查验收标准 → 派审查子代理 → 修掉 CRITICAL / HIGH → 把任务改成 `Review`，附上证据。有远程仓库时开 PR，CI 通过才合并。
4. **交接**：会话结束前更新 `docs/STATUS.md`。下一个 Agent 只读它就要能接上。
5. **记决定**：选型或改架构时写 `docs/adr/`；查过的外部资料写进 `docs/research/`，附出处链接和查询日期。
6. **记教训**：同一类错误出现第二次，就把它变成一条检查（测试、CI 或 hook），不要只加一句提醒。

## 什么时候停下来问人

- 要花钱的调用第一次运行之前（先给出估算：次数 × 单价）。
- 要往外发的东西：推送到远程仓库、发消息给真人、发布内容。
- 说明书和代码现状冲突，或者验收标准做不到。
- 改动会碰到别的任务正在改的文件。
