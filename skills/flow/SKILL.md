# flow

前提：项目根目录有 `AGENTS.md`、`docs/STATUS.md` 和 `docs/BOARD.md`。没有的话，先运行 `/agent-project-kit:project-init`。

项目特有的信息都从 `AGENTS.md` 里读，这个 skill 本身不写死任何项目细节：

- **完成的定义**：「命令」一节下面的那一行，也就是要跑哪些检查。
- **共享文件**：「代码地图」一节下面的那一行。
- **代码地图**：哪个目录属于哪条主线。
- **编号规则**：`docs/BOARD.md` 顶部的说明。

每个动作都以**更新文件**结束。状态只认文件，不认聊天记录。

先看参数，选择对应的一节执行。没有参数时，执行 `next`。

---

## new &lt;想法&gt;：想法 → 说明书

1. 读 `docs/BOARD.md`，按顶部的编号规则，在所有表格里找出同一主线的最大编号，新编号在它基础上加一。编号不复用。
2. 复制 `docs/specs/_TEMPLATE.md` 为 `docs/specs/T-xxx-<英文短名>.md`，填写目标、验收标准、允许改动、不做。
   - 验收标准必须每条都能验证，并写明验证方法。写不出来，说明想法还不清楚：先问用户，最多问 3 个问题。
   - 「允许改动」对照 AGENTS.md 的代码地图。涉及共享文件时写进「需要总控配合」，不要列为允许改动。
3. 在 BOARD 加一行：说明书完整的放进 `Ready`，否则放进 `Inbox`；有前置依赖的放进 `Blocked` 并写明卡在哪。
4. 向用户汇报编号、一句话目标，以及能否和正在进行的任务并行。

## next：下一步做什么（总控用）

1. 读 `docs/STATUS.md` 的「当前」和「开放问题」，以及 `docs/BOARD.md`。
2. 列出 `Ready` 的任务，按依赖关系和价值排序。
3. 判断哪些可以并行：「允许改动」的目录互不重叠，且都不碰共享文件。同时进行的任务最多 3 个（包括已经 In progress 的）。
4. 有需要用户做的事（开放问题、需要他本人操作的杂务），放在最前面。
5. 输出建议：先做哪个、哪些可以各开一个会话并行。在 Claude 桌面端可以用 `start_session` 为每个并行任务各开一个会话：仓库已有提交时用 worktree；没有提交或要共用目录时，在简要说明里写明「不切换分支、不提交、只改说明书允许的文件、不改 BOARD 和 STATUS」。简要说明的开头写「先读 AGENTS.md，然后执行 flow start T-xxx」。

## start T-xxx：开工

1. 读 `AGENTS.md`、`docs/STATUS.md` 和任务说明书。说明书不存在或任务不在 `Ready`，就停下来告诉用户。
2. 检查冲突：BOARD 上其他 `In progress` 任务的「允许改动」与本任务重叠时，停下来报告。说明书写着「由总控执行」的任务（只改共享文件），只能在总控会话里做；当前是执行者会话时，停下来告诉用户。
3. 建分支：`git switch -c task/T-xxx-<短名>`。如果已经在 worktree 会话里，或者简要说明里要求不切换分支，就沿用当前分支，并把分支名记进 BOARD。
4. 把 BOARD 里这一行移到 `In progress`，填上「谁在做」（会话名或人名）和分支。简要说明里要求不改 BOARD 的，跳过这一步，在最后的汇报里说明。
5. 测试先行：先写失败的测试，再写实现。只改说明书允许的文件。调研类任务不写代码，产出写进 `docs/research/`，可以派 `vendor-researcher` 子代理去做。
6. 中途发现说明书不对（做不到、范围不够），先改说明书并告诉用户，不要悄悄扩大范围。

## finish：收尾

1. 运行 AGENTS.md「完成的定义」里的全部检查，都必须通过，并把输出摘要留作证据。
2. 逐条核对说明书的验收标准，每条写下证据（测试名、命令输出、截图路径）。做不到的条目如实标出，不要勾选。
3. 派审查子代理（例如 `code-reviewer`，或对应语言的 reviewer）。改动碰到密钥、外部 API、用户输入、文件或网络输入时，加派 `security-reviewer`。只把代码和说明书交给审查者，不要附上你自己的结论。核实它的每条发现，修掉确认存在的 CRITICAL 和 HIGH。调研类任务跳过这一步，改为检查每条结论都有出处。
4. 填写说明书末尾的「结果」一节：分支、证据、遗留问题。
5. BOARD：这一行移到 `Review`，附上证据摘要。如果当前就是总控会话并且已经合并，直接移到 `Done`。
6. STATUS：在验收记录里加一行；「能用的 / 没做的」有变化时同步更新。
7. 做过选型或架构决定的，用 `docs/adr/_TEMPLATE.md` 写一份 ADR。查过外部资料的，确认已经写进 `docs/research/`。
8. 只有用户要求时才提交。提交信息格式为 `<类型>: T-xxx 简述`，类型可以是 feat、fix、refactor、docs、test、chore。

## handoff：会话结束前交接

1. 重写 `docs/STATUS.md` 的「当前」一节，只写事实：阶段、能用的、没做的、下一步、待拍板。末尾写更新日期和更新者。
2. 这次会话踩到的坑，追加到「已知的坑」，一条一句，写清楚怎么绕过。
3. 新冒出来、需要用户决定的问题，追加到「开放问题」。已经解决的问题删掉，并把结论写进 ADR 或说明书。
4. 检查 BOARD 和实际是否一致：没人在做却标着 `In progress` 的，改回 `Ready` 并注明做到哪一步。
5. 检查改动的文件里没有密钥、Token 或个人数据。
6. 用三句话告诉用户：做了什么、现在什么状态、下一步是什么。

---

## 不要做

- 不要在 STATUS 里写计划中的愿望，也不要把「应该能用」写成「能用」。没验证过的标「未验证」。
- 不要把密钥、Token、个人数据写进任何文档。
- 不要在执行者会话里改共享文件，要写进「需要总控配合」。
- 不要同时开超过 3 个并行任务。
