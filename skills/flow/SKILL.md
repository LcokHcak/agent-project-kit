# flow

前提：项目根目录有 `AGENTS.md`、`docs/STATUS.md` 和 `docs/BOARD.md`。没有的话，先运行 `/agent-project-kit:project-init`。

项目特有的信息都从 `AGENTS.md` 里读，这个 skill 本身不写死任何项目细节：

- **完成的定义**：「命令」一节下面的那一行，也就是要跑哪些检查。
- **共享文件**：「代码地图」一节下面的那一行。
- **代码地图**：哪个目录属于哪条主线。
- **编号规则**：`docs/BOARD.md` 顶部的说明。

每个动作都以**更新文件**结束。状态只认文件，不认聊天记录。

先看参数，选择对应的一节执行。没有参数时，执行 `next`。

**体检脚本**：下面多处要跑它。项目里有 `scripts/kit-check.mjs` 就用 `node scripts/kit-check.mjs`；没有就用插件自带的 `node "${CLAUDE_SKILL_DIR}/../../scripts/check.mjs" <项目根目录>`（也就是本 skill 目录往上两级、插件根目录下的 `scripts/check.mjs`）。没有 Node 时跳过，并在汇报里说明没跑。

## new &lt;想法&gt;：想法 → 说明书

1. 读 `docs/BOARD.md`，按顶部的编号规则，在所有表格里（包括 `Voided`）找出同一主线的最大编号，新编号在它基础上加一。编号不复用。
2. 复制 `docs/specs/_TEMPLATE.md` 为 `docs/specs/T-xxx-<英文短名>.md`，填写目标、验收标准、允许改动、花费与风险、不做。
   - 验收标准必须每条都能验证，并写明验证方法。写不出来，说明想法还不清楚：先问用户，最多问 3 个问题。
   - 「允许改动」对照 AGENTS.md 的代码地图。涉及共享文件时写进「需要总控配合」，不要列为允许改动。
   - 任务里有付费调用时，在「花费与风险」里写估算（次数 × 单价）。
   - 想法其实是「在几个方案里用数据选一个」时，类型写「实验」，并用 `docs/experiments/_TEMPLATE.md` 先把判定标准写好。
3. 在 BOARD 加一行：说明书完整的放进 `Ready`，否则放进 `Inbox`；有前置依赖的放进 `Blocked` 并写明卡在哪。项目有 `docs/plan/exec-plan.md` 时，把任务补进对应的阶段。
4. 向用户汇报编号、一句话目标，以及能否和正在进行的任务并行。

## next：下一步做什么（总控用）

1. 跑体检脚本。有错误时先列出来并修掉（任务板和文件对不上时，下面的建议也不可信）；提醒如实转告用户。
2. 读 `docs/STATUS.md` 的「当前」和「开放问题」，以及 `docs/BOARD.md`。有 `docs/plan/exec-plan.md` 时也读它：当前在哪个阶段、离「走完的标志」还差什么、哪些决定还没拍板。
3. 列出 `Ready` 的任务，按依赖关系和价值排序。
4. 判断哪些可以并行：「允许改动」的目录互不重叠，且都不碰共享文件。同时进行的任务最多 3 个（包括已经 In progress 的）。
5. 有需要用户做的事（开放问题、待拍板的决定、需要他本人操作的杂务），放在最前面。
6. 输出建议：先做哪个、哪些可以各开一个会话并行、每个任务适合用哪一档模型（写说明书和评审用最强的，按说明书实现用主力编码模型，调研用便宜的）。在 Claude 桌面端可以用 `start_session` 为每个并行任务各开一个会话：仓库已有提交时用 worktree；没有提交或要共用目录时，在简要说明里写明「不切换分支、不提交、只改说明书允许的文件、不改 BOARD 和 STATUS」。简要说明的开头写「先读 AGENTS.md，然后执行 flow start T-xxx」。

## start T-xxx：开工

1. 读 `AGENTS.md`、`docs/STATUS.md` 和任务说明书。说明书不存在或任务不在 `Ready`，就停下来告诉用户。
2. 检查冲突：BOARD 上其他 `In progress` 任务的「允许改动」与本任务重叠时，停下来报告。说明书写着「由总控执行」的任务（只改共享文件），只能在总控会话里做；当前是执行者会话时，停下来告诉用户。
3. 建分支：`git switch -c task/T-xxx-<短名>`。如果已经在 worktree 会话里，或者简要说明里要求不切换分支，就沿用当前分支，并把分支名记进 BOARD。
4. 把 BOARD 里这一行移到 `In progress`，填上「谁在做」（会话名或人名）和分支。简要说明里要求不改 BOARD 的，跳过这一步，在最后的汇报里说明。
5. 测试先行：先写失败的测试，再写实现。只改说明书允许的文件。调研类任务不写代码，产出写进 `docs/research/`，可以派 `vendor-researcher` 子代理去做。
6. 任务里有付费调用（模型、语音识别、云服务）时：常规测试用假实现或录制的响应；真实调用放在单独的脚本里，第一次运行前把估算（次数 × 单价）告诉用户并等他确认；每次调用都要留下追踪记录（模型、提示词版本、token、费用、耗时）。
7. 中途发现说明书不对（做不到、范围不够），先改说明书并告诉用户，不要悄悄扩大范围。

## finish：收尾

1. 运行 AGENTS.md「完成的定义」里的全部检查，都必须通过，并把输出摘要留作证据。
2. 逐条核对说明书的验收标准，每条写下证据（测试名、命令输出、截图路径）。做不到的条目如实标出，不要勾选。
3. 派审查子代理（例如 `code-reviewer`，或对应语言的 reviewer）。改动碰到密钥、外部 API、用户输入、文件或网络输入时，加派 `security-reviewer`。只把代码和说明书交给审查者，不要附上你自己的结论。核实它的每条发现，修掉确认存在的 CRITICAL 和 HIGH。调研类任务跳过这一步，改为检查每条结论都有出处。
4. 问自己一句：这次踩到的坑、审查发现的问题，有没有哪一条能让机器以后自动拦住？能，就加一条测试或检查，并在 AGENTS.md 对应的规则后面注明由什么检查（AGENTS.md 是共享文件，执行者会话里写进「需要总控配合」）。不能，再考虑写进 STATUS 的「已知的坑」。
5. 填写说明书末尾的「结果」一节：分支、证据、新增的回归用例或检查、实际花费、遗留问题。
6. BOARD：这一行移到 `Review`，附上证据摘要。如果当前就是总控会话并且已经合并，直接移到 `Done`，写上完成日期和证据。
7. STATUS：在验收记录里加一行；「能用的 / 没做的」有变化时同步更新。
8. 做过选型或架构决定的，用 `docs/adr/_TEMPLATE.md` 写一份 ADR。查过外部资料的，确认已经写进 `docs/research/`。
9. 跑体检脚本，错误必须清零。
10. 只有用户要求时才提交、推送或开 PR。提交信息格式为 `<类型>: T-xxx 简述`，类型可以是 feat、fix、refactor、docs、test、chore。有远程仓库时，一个任务一个 PR，按 `.github/pull_request_template.md` 填写，CI 通过后才合并。

## handoff：会话结束前交接

1. 重写 `docs/STATUS.md` 的「当前」一节，只写事实：阶段、能用的、没做的、下一步、待拍板。末尾写「更新于 YYYY-MM-DD，由谁更新」（体检脚本靠这个日期判断交接单是否过期）。
2. 这次会话踩到的坑，追加到「已知的坑」，一条一句，写清楚怎么绕过。
3. 新冒出来、需要用户决定的问题，追加到「开放问题」。已经解决的问题删掉，并把结论写进 ADR 或说明书。
4. 跑体检脚本，按结果修正 BOARD 和实际不一致的地方：没人在做却标着 `In progress` 的，改回 `Ready` 并注明做到哪一步；不做了的任务移到 `Voided` 并写明原因。
5. 检查改动的文件里没有密钥、Token 或个人数据。
6. 用三句话告诉用户：做了什么、现在什么状态、下一步是什么。

## case &lt;哪里错了&gt;：把一次出错存成回归用例

用户在真实使用中发现结果不对时用。**先留用例，再谈修复。**

1. 弄清楚三件事：输入是什么、期望什么、实际得到了什么。对话里已经有的不要再问；缺的最多问 2 个问题。
2. 判断是哪一类：
   - **代码的 bug**（同样的输入每次都错）：在项目的测试目录里写一个能重现它的失败测试，运行一次，确认它确实失败，而且失败的原因就是这个 bug。
   - **模型输出的错**（代码没错，但模型的摘要、分类、抽取结果不对）：复制 `evals/cases/_TEMPLATE.md` 为 `evals/cases/C-xxx-<英文短名>.md`（编号取现有最大值加一），填写输入、期望、实际、怎么判定，以及当时的模型和提示词版本（能从追踪记录里查到就查）。项目里还没有 `evals/` 时，先建这个目录和一份说明，再存用例。
3. 输入里的真实姓名、联系方式、密钥和不该外传的内容，先替换成占位内容再写进文件。拿不准能不能存，问用户。
4. 不要顺手修。修复是一个任务：小的直接问用户「现在修吗」；大的用 `new` 开一个任务，说明书的验收标准里写上「C-xxx 通过」或那个失败测试的名字。
5. 向用户汇报：用例存在哪、它现在是失败的、接下来怎么修。

## check：体检

1. 跑体检脚本。它检查这些：
   - **错误**：缺 `AGENTS.md` / `docs/STATUS.md` / `docs/BOARD.md`；还有没替换的 `{{占位符}}`；任务板上编号重复；`Ready` / `In progress` / `Review` 里的任务找不到说明书（类型为「杂务」的除外）；`AGENTS.md`、`CLAUDE.md`、`docs/`、`evals/` 里的相对链接指向不存在的文件（区分大小写）。
   - **提醒**：交接单超过 14 天没更新或没写更新日期；同时进行的任务超过 3 个；`In progress` 没写谁在做；`Done` 没写证据；说明书对应的任务不在任务板上；`AGENTS.md` 超过 200 行。
2. 错误逐条修掉。修的时候以事实为准：先看文件和 git 记录确认真实情况，再改任务板或文档；不要为了让检查通过而编造内容（例如给没验证过的任务补一条「证据」）。
3. 提醒逐条判断：确实是问题就修，不是问题就向用户说明原因。
4. 再跑一遍，把最终输出告诉用户。
5. 用户想让它自动执行时：把脚本复制到项目的 `scripts/kit-check.mjs`，在 CI 里加一步 `node scripts/kit-check.mjs`（共享文件，由总控改）。

## 不要做

- 不要在 STATUS 里写计划中的愿望，也不要把「应该能用」写成「能用」。没验证过的标「未验证」。
- 不要把密钥、Token、个人数据写进任何文档，包括回归用例和追踪记录。
- 不要在执行者会话里改共享文件，要写进「需要总控配合」。
- 不要同时开超过 3 个并行任务。
- 不要在没有估算和用户确认的情况下跑付费调用。
- 不要删除或改写已有的回归用例来让评测通过；用例错了要说明原因并告诉用户。
